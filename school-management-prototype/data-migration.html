存量数据迁移与接口契约

这套结构上线时，库里已经有用户、有绑定关系、有课程和成绩了。下面是迁移路径和接口定义。

!
迁移里唯一真正难的一步是「业务数据归属」。
已经绑了两所学校的用户，他们的课程和成绩是在没有学校维度的情况下产生的。这些数据归哪一所，是必须提前定规则的事，不能上线时再想。

一、现状与目标态

维度现状（推测）目标态
学校绑定一张绑定表，或 user 表上的字段，允许多人多校user_school 认证关系表，带 auth_status 与 is_primary
学籍信息直接挂在绑定关系上拆到 user_enrollment，支持一校多阶段
主学校不存在这个概念user.primary_school_id，全局唯一
业务数据只挂 user_id，没有学校维度挂 user_enrollment_id + 冗余 school_id

二、迁移六步

步骤做什么要点
0 · 盘点 统计分布 先出三个数：每人绑定学校数的分布（1 所 / 2 所 / 3+）、业务表总量、按现有线索能直接归属的比例。这三个数决定后面要不要开人工队列。
1 · 建关系 回填 user_school 从现有绑定关系生成，auth_status = active，authed_at 沿用原绑定时间，不要写成迁移当天
2 · 建学籍 回填 user_enrollment 每所学校的学籍字段生成一条 enrollment，is_current = true。学历层次若原表没有，先置"未知"并进补全队列，不要瞎猜
3 · 归属 回填业务表 最难的一步，见下一节
4 · 主学校 指定 primary 自动取"最近一次认证且未解绑"的学校，脚本直接写入，不做首登确认。用户觉得不对可以自己切（切换主学校是已有能力）
5 · 校验 跑断言 见第四节。断言不通过就不发布

三、业务数据归属怎么定

按用户的绑定情况分三档处理，优先级从确定到不确定：

情况处理方式
只绑了 1 所学校 直接归到那一所。零歧义，预计覆盖绝大多数用户
绑了多所，记录上有线索 按线索归属：课程 ID 前缀、考试场次、成绩单里带学号的快照字段、日志里的学校上下文。有线索就用，不要用时间猜
绑了多所，且无线索 按认证时间窗归属：记录创建时间落在 A 校认证期内的归 A，落在 B 校认证期内的归 B
仍然判断不出 留空，进人工队列。school_id = NULL, needs_review = 1，不要默认归给最近认证的那所
!
留空比猜错好。猜错的后果是把 A 校的成绩挂到 B 校，用户看到的是"我的成绩串了"，而且很难被发现和纠正；留空的后果只是"这条记录暂时不显示"，可修复且可统计。人工队列的数量本身就是迁移质量指标。

四、校验断言

  • 每条 active 的 user_school 至少有一条 is_current = true 的 enrollment。
  • 每个用户至多一条 is_primary = true；迁移后不存在 primary_school_id 为空却有多校关系的用户。
  • 业务表无孤儿：所有 user_enrollment_id 都能 join 到 user_enrollment。
  • 迁移前后行数守恒：业务表总行数不变，只有归属字段被填充。
  • 抽样比对：随机取 500 个单校用户，迁移后按主学校查询的结果应与迁移前完全一致。
  • needs_review = 1 的占比低于阈值（比如 0.5%）才允许发布，否则先人工清理。

五、灰度与回滚

阶段动作
加字段先加可空字段与索引，不动数据、不改代码。此时读写都还是老逻辑，随时可回退
回填 + 校验跑迁移脚本，输出校验报告。保留迁移前的字段快照表，回滚脚本必须可逆
双写新代码写入业务数据时同时写 user_enrollment_id 与 school_id，读取仍走老路径
切读按用户灰度切到新查询路径，观察错误率与"数据串校"类客服反馈
收紧全量稳定后，字段改为非空 + 补唯一约束。这一步之后才真正不可回退，前面每一步都可以退

六、接口契约

方法路径说明与关键约束
GET /api/me/schools 返回认证关系列表 + 每校的学籍阶段 + 数据量统计 + is_primary。前端首屏只需要这一个接口
POST /api/me/schools/{id}/primary 切换主学校。幂等：重复提交同一个目标学校返回成功。并发：靠 uk_user_primary 唯一索引兜底，两个端同时切换只会有一个成功，另一个返回 PRIMARY_CONFLICT 由前端重试
POST /api/me/schools/{id}/unbind/code 发送解绑验证码。必须做频控：同一手机号 60 秒一次、每天上限；返回 code_ttl 供前端倒计时
POST /api/me/schools/{id}/unbind 提交解绑。入参只有 code。解绑主学校时，服务端自动把主学校切到剩余学校里最近认证的一所，不需要前端传新主学校；响应里返回切换后的 primary_school_id 供前端提示。服务端必须重新校验"是否最后一所学校"，不能只靠前端禁用按钮
POST /api/me/schools/{id}/enrollments 重新认证。带 mode：update 更新当前阶段 / add 新增学历阶段。新增时服务端要把该校其它阶段置为 is_current = false，并用 uk_enrollment_current 保证唯一

错误码至少要覆盖这些，前端才好给准确提示：

错误码触发场景 / 前端应对
SCHOOL_NOT_BOUND学校不存在或已解绑。刷新列表
LAST_SCHOOL_CANNOT_UNBIND只剩一所学校。按钮置灰并给出原因
CODE_INVALID / CODE_EXPIRED验证码错误或过期。清空输入框，提示重新获取
CODE_ATTEMPTS_EXCEEDED验证码错误次数过多。锁定并要求重新发送
PRIMARY_CONFLICT并发切换冲突。静默重试一次，仍失败则提示稍后再试
ENROLLMENT_DUPLICATE同一学校内该学号已被本人或其他账号占用
