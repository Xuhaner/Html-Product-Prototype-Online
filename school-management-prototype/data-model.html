账号数据归属方案

对应「解绑学校」与「切换学校」两个功能点背后的数据设计。结论先行，后面是可讨论项。

✓
一句话结论：学校是「数据分区」，不是「数据快照」；主学校只是一个指针。
切换学校 = 换一个查询条件，不搬数据、不合并、不覆盖。所以「切回来数据还在」不是额外做的功能，而是这套设计天然的结果。

一、三个方案，为什么只选第一个

方案行为专升本场景下会发生什么结论
A · 独立保存 每所学校一份数据，主学校决定默认展示哪一份 专科成绩完整保留，本科成绩独立累计，互不干扰 采用
B · 以最新为准 切换后新学校数据覆盖旧的 专科成绩、学分永久丢失，且不可逆 不可用
C · 合并展示 两所学校的数据混在一起 学分与 GPA 会算错；两校课程重名时无法区分 不可用

方案 B 的问题不只是"体验不好"：学籍、成绩属于重要数据，覆盖式切换一旦误操作就永久丢数据，同时也不满足教育数据的留存要求。所以 覆盖式切换在方案层面就该排除，而不是靠二次确认弹窗去兜底。

二、数据分四层

① 账号级
user 表 · 跨学校共享
  • 账号、手机号、微信
  • 头像、昵称、性别、个人介绍
  • 安全设置、消息偏好
② 认证关系
user_school · 用户 × 学校
  • 你在哪几所学校认证过
  • 认证状态、认证 / 解绑时间
  • 主学校标记 is_primary
③ 学籍阶段
user_enrollment · 学历阶段
  • 学号、姓名、学院、专业、班级
  • 学历层次、入学年份、在读 / 毕业
  • 专升本 = 同一所学校下的第二个阶段
④ 主学校指针
user.primary_school_id
  • 全局唯一，同一时间只有一所
  • 切换 = 一次 UPDATE
  • 不承载任何业务数据

三、为什么学籍要单独一张表

这是这版方案里最容易做错的地方。最初的想法是"一张 user_school 表装下认证关系 + 学籍信息"，用 (user_id, school_id) 做唯一索引。但这条索引会直接挡掉一个真实场景：

!
同一个人在同一所学校读了专科，又专升本读了本科。
学校没变，但学号、学院、专业、学历层次全变了。此时 (user_id, school_id) 唯一索引会拒绝第二条记录；如果为了塞进去而覆盖原记录，专科阶段的成绩就找不到归属了。

所以要把两件事拆开：「你在这所学校认证过」和「你在这所学校的哪个学历阶段」是两层关系。前者是认证关系（一人一校一条），后者是学籍阶段（一人一校可以有多条）。业务数据（课程、考试、成绩）挂在学籍阶段上，而不是挂在学校上——这样专科的课归专科、本科的课归本科，跨阶段学分天然不会互相折算。

场景关系怎么变
专升本，换学校新增一条 user_school（新学校）+ 一条 enrollment。原学校的关系与学籍都不动
专升本，同一所学校user_school 不变，新增一条 enrollment，旧的 enrollment 置 is_current = false
本硕连读 / 读研同上，学历层次从本科变为硕士
学号填错了更新当前 enrollment 的字段，不新增记录

四、七条硬规则

  • 主学校唯一。约束 primary_school_id 必须指向一条"已认证且未解绑"的 user_school，不允许为空（除非一所都没有）。
  • 所有业务表必须带归属维度。课程、考试、成绩挂 user_enrollment_id；高频查询再冗余一个 school_id 做过滤，避免每次两层 join。
  • 一所学校下同时只有一个"当前阶段"。用 is_current 标记，唯一约束保证不会出现两个。
  • 切换主学校不产生任何数据迁移，也不需要重新认证。认证关系是"用户 × 学校"，与谁是主学校无关。
  • 解绑是软删除。auth_status 从 active 改为 unbound，认证关系下的所有学籍阶段与业务数据保留 90 天。
  • 解绑主学校时自动切换。自动切到剩余学校里最近认证的一所，并明确告知用户切到了哪一所；只剩一所时禁止解绑。
  • 重新认证同一所学校要能复用原关系。按 (user_id, school_id) 命中历史记录，只更新或新增学籍阶段，不新建认证关系——这正是软删除存在的理由。

六、容易踩的坑

  • 同一个人在两所学校的姓名可能不一样。当前截图里就是「wxh26」和「王东喜」。昵称、头像归账号级，学籍姓名归学籍阶段，两者不能互相覆盖。
  • 专升本不是"改学籍"，是新增一个学历阶段。原阶段必须保持可查，否则学历档案就断了。
  • 主学校被解绑后必须有兜底。不能出现 primary_school_id 指向已解绑学校的中间状态。
  • 业务数据不能只挂学校。否则同一所学校内专升本后，专科和本科的课程会混在一起算学分。
  • 消息通知要标来源学校与阶段。解绑后，来自该校的历史通知是隐藏还是保留，需要定。
  • 数据导出要能按学校 / 按阶段选。否则导出全部时会混淆不同阶段的成绩。

七、已确认的决策

下面 7 条已经确认，按"规则尽量少"的原则定稿。原型与接口文档都已按这个结论实现。

#决策点结论说明
1是否提供"彻底删除数据"的入口不做只保留软删除 + 90 天可恢复，不开放不可逆的删除操作
2数据保留期时长维持 90 天按现方案执行，不额外调整
3解绑主学校时如何确定新主学校自动切换自动切到剩余学校里最近认证的一所，弹窗中明确告知切到了哪一所；不要求用户手动选择
4是否限制绑定学校数量不限制不加数量上限
5是否提供"全部学校"汇总视图不做数据视角只提供单校视图，通过切换学校查看不同学校的数据
6跨学历阶段的学分是否折算不折算各阶段学分独立计算，不引入"学分认定"关系表
7解绑是否需要填写原因不填短信验证码 + 二次确认即可，服务端保留操作日志便于追溯
i
一条连带影响值得记一下：不限制绑定数量、同时又不提供汇总视图，意味着绑了 3 所以上的用户只能靠"切换"逐所查看。如果后续收到"找不到另一所学校数据"的反馈，第一个该补的是学校列表里的数据量提示，而不是把汇总视图加回来。
